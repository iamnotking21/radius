# Radius BLE Key Schedule — v0.1

**Owner:** ble-protocol · **Implements:** safety invariant 5 · **Binds:** ADR-004, **ADR-008**
**Vectors:** `vectors/key_schedule.json` (derivation, unchanged) ·
`vectors/key_rotation.json` (key ring + seam, new in v0.1)

**Changed in v0.1 (2026-08-04):** `account_key` provenance is settled — it is
**server-issued** (ADR-008, decision 32). §2 rewritten. §8 (rotation protocol),
§9 (multi-device), §10 (threat model) are new. §4.3 and §5 sharpened because B8
is now the top technical risk under android-first (decision 33).

> **Nothing on air changed.** Not one byte, not one bit, not one timing
> parameter. The derivation function is identical; only the origin of its input
> moved. Safety invariants 4 and 5 are untouched, which is what ADR-008 asserts
> and what §10.1 re-verifies field by field. If any future change to issuance
> would alter the frame, that is a much larger decision than ADR-008 authorised
> and it stops at this document.

Structure follows the Apple/Google Exposure Notification design, which is the
most heavily audited proximity-privacy key schedule ever deployed. **We diverge
from EN in exactly one place and it is the important one: EN's root key never
leaves the device. Ours is issued by, and retained by, the server (§2, §10).**

```
account_key        32 B, SERVER-ISSUED and server-RETAINED (ADR-008).
   │               NEVER broadcast. Delivered to the device exactly once (§2.2).
   │  HKDF-SHA256(info = "daily-key" || day)
   ▼
daily_key(d)       32 B, rotates every UTC day
   │  HKDF-SHA256(info = "ephemeral-id" || day || epoch)
   ▼
ephemeral_id(d,e)  16 B, rotates every 15 minutes. THIS, and only this, is broadcast.
```

## 1. Parameters, exactly

All derivations use **HKDF-SHA256** (RFC 5869, extract-then-expand). The
reference values in `vectors/key_schedule.json` were generated with OpenSSL
3.5.6, verified first against RFC 5869 test case 1.

**Salt — identical for both derivations:**

```
salt = ASCII "radius/ble/v0"                       (13 bytes)
     = 72 61 64 69 75 73 2F 62 6C 65 2F 76 30
```

The salt is the protocol domain separator. It is not secret. It changes only if
the protocol version changes, and changing it invalidates every derived key —
which is the intent, since a v1 device must not derive v0 identities.

**Daily key:**

```
daily_key(d) = HKDF-SHA256(
    IKM  = account_key,                            (32 bytes)
    salt = "radius/ble/v0",
    info = ASCII "daily-key" || uint32be(d),       (9 + 4 = 13 bytes)
    L    = 32 )

info prefix = 64 61 69 6C 79 2D 6B 65 79
d = floor(unix_seconds / 86400)                    UTC days since the Unix epoch
```

**Ephemeral ID:**

```
ephemeral_id(d,e) = HKDF-SHA256(
    IKM  = daily_key(d),                           (32 bytes)
    salt = "radius/ble/v0",
    info = ASCII "ephemeral-id" || uint32be(d) || uint16be(e),   (12 + 4 + 2 = 18 bytes)
    L    = 16 )

info prefix = 65 70 68 65 6D 65 72 61 6C 2D 69 64
e = floor((unix_seconds mod 86400) / 900)          epoch index, 0..95
```

`d` is included in the ephemeral-ID `info` as well as in the daily-key `info`.
This is redundant — `daily_key` already commits to `d` — and it is deliberate.
It costs four bytes of `info` and it means a mis-derived `daily_key` can never
silently produce a valid-looking ephemeral ID for a different day.

**Epoch index is UTC-day-relative, not absolute.** `e` resets to 0 at 00:00 UTC.
`e = 96` is impossible and any implementation producing it has a clock bug; it
MUST be treated as a fault, not clamped.

### 1.1 Worked example (from the vectors)

```
account_key = 000102…1f
t           = 2026-08-04T00:15:00Z  →  unix 1785802500  →  d = 20669, e = 1

daily_key(20669)        = d47f9991c1465914d8224196255811479c5816e630984199496e84d83bdfa68d
ephemeral_id(20669, 1)  = a1e38f76e2380e9590fefb156e6f8874
```

`vectors/key_schedule.json` additionally asserts the properties that matter:
the ID is constant across a 15-minute epoch, changes at the epoch boundary, and
changes at the UTC day boundary because the daily key changed.

## 2. Where `account_key` comes from — SETTLED: server-issued (ADR-008)

**`account_key` is 32 bytes from a server-side CSPRNG, generated by the server,
retained by the server, and delivered to the device exactly once over a
certificate-pinned channel.** ADR-008, decision 32. This closes blocker B10 and
open question 6 of `SPEC.md` §10.

This spec previously stated the opposite and recommended device-generated keys.
That recommendation was overruled by the founder with the cost stated in advance
and recorded in full in ADR-008 §"What this costs". **It is not relitigated
here.** What follows is the engineering that makes the decision implementable
and the honesty that makes it defensible.

The one-line summary a reviewer needs: *the operator can derive every ephemeral
ID any account will ever broadcast, past and future; a third-party observer on
the air still learns nothing.* §10 is the threat model that says this precisely.

### 2.1 What this changed in the protocol — and what it did not

| | Status |
|---|---|
| Derivation function, salt, `info` strings, output lengths | **UNCHANGED** |
| Frame layout, 19 bytes, field order (invariant 4) | **UNCHANGED** |
| eid ↔ RPA co-rotation requirement (invariant 5) | **UNCHANGED** |
| Rotation period, UTC synchronisation, no-jitter rule | **UNCHANGED** |
| Resolution, skew window, replay window | **UNCHANGED** |
| Existing conformance vectors (all 65) | **UNCHANGED — not one value moved.** See `vectors/index.json` `unaffected_by_ADR_008`. |
| Origin and custody of `account_key` | **CHANGED** — §2.2, §2.3 |
| Rotation: previously undefined, now a required, specified protocol | **NEW** — §8 |
| Multi-device: previously impossible, now possible and therefore a new hazard | **NEW** — §9 |
| Threat model: the operator is now inside it | **CHANGED** — §10 |

Because the derivation is byte-identical, **no vector was regenerated.** A
conformance suite tests the function `(account_key, day, epoch) → eid`. HKDF
does not know or care who produced its input. Regenerating 65 files to record a
provenance change would have destroyed the one property that makes vectors
useful — that a diff in a vector file means a diff in behaviour.

### 2.2 Issuance path (ADR-008 M7) — once, pinned, never re-fetchable

```
account creation (or re-issuance, §2.4):
  1. server generates 32 B from a CSPRNG                       server side only
  2. server stores it per M1/M2 (own table, DEK in OpenBao)
  3. server returns it in the response to ONE specific RPC,
     on a certificate-pinned TLS channel                       the only transit, ever
  4. device stores it per §2.3 and ACKs
  5. server marks the key delivered
```

Normative rules:

- **The key crosses the network exactly once per issuance.** There is no
  "fetch my key" endpoint, no "re-sync key" endpoint, no admin "resend" action,
  and no debug build that adds one. A re-fetchable key turns every account
  takeover into a permanent identity compromise, which is the specific thing M7
  exists to prevent.
- **Delivery is on a certificate-pinned channel only.** If pinning is
  unavailable or fails, issuance MUST fail closed. A device that cannot pin does
  not get a key and cannot use Radar. It does not fall back to system trust.
- **`account_key` MUST NOT appear in any other RPC response, ever**, including
  profile, session, sync, entitlement, and diagnostic responses. This is a
  review item on every backend PR that touches the accounts or radar surface,
  the same way "no security permissions on GATT characteristics" is a review
  item on radio PRs (`SPEC.md` §7.3).
- **`account_key` MUST NOT be logged, traced, or sampled** on either side.
  Not at DEBUG, not redacted-to-first-4-bytes, not in a span attribute. Four
  bytes of a 32-byte key in a log aggregator is four bytes more than zero, and
  the value is by construction the most sensitive number in the system.
- The delivering RPC MUST be rate-limited and MUST emit an audit row per M3.
  Issuance is a security event, not a CRUD operation.

**Ordering rule that matters for the state machine:** a device MUST NOT enter
`SCAN` or begin advertising before issuance has completed and been ACKed. There
is no "advertise with a locally generated placeholder and reconcile later" path.
A placeholder would produce eids no resolver accepts — harmless — and would
train implementers to treat the root key as optional, which is not harmless.

### 2.3 What the device stores, and where — Android (first-class)

`account_key` is raw key material that must be readable in plaintext by the app
process at every epoch boundary, because HKDF-Extract uses it as the *message*
input (`HMAC(key = salt, data = account_key)`), not as the HMAC key. **Android
Keystore cannot perform this operation on a non-exportable key.** There is no
way to keep the root key inside the TEE and still derive from it with this
schedule. Stating that plainly rather than implying hardware protection we do
not have:

```
account_key (32 B plaintext)
   └─ AES-256-GCM encrypted with `radius_ak_wrap`
        `radius_ak_wrap` = AES key generated IN Android Keystore, non-exportable
                           StrongBox-backed where the device supports it
   └─ ciphertext + IV written to a dedicated file in app-private storage
```

Normative rules for the Android implementation (`android-kotlin` owns the code;
this document owns the requirement):

- `radius_ak_wrap` is generated in Keystore with `setIsStrongBoxBacked(true)`,
  catching `StrongBoxUnavailableException` and falling back to TEE-backed.
  **Which backing was obtained MUST be recorded as a per-model rig
  observation**, exactly like §4.3 — StrongBox availability is OEM-variable and
  we should not discover its distribution in production.
- `setUserAuthenticationRequired(false)` and `setUnlockedDeviceRequired(false)`.
  **This is a real weakening and it is forced**: the radio must derive the next
  eid at a UTC boundary with the screen off and the device locked. Binding the
  wrap key to device-unlocked would stop background advertising dead. What we
  therefore get is protection against filesystem-level extraction and against
  backup exfiltration — **not** protection against a compromised running app
  process or a rooted device. Do not describe it as more than that internally or
  externally.
- The ciphertext lives in its **own file**, not in the SQLDelight/SQLCipher
  database. A database compromise must not be a root-key compromise; they are
  separate failure domains and must stay separate.
- `android:allowBackup="false"` **and** an explicit `dataExtractionRules`
  exclusion for the key file, covering both cloud backup and device-to-device
  transfer. The wrapped blob would be undecryptable off-device anyway (the
  Keystore key does not travel), but shipping our key material to a third party's
  cloud for no benefit is a gratuitous addition to the threat model.
- `daily_key` MAY be cached in the encrypted local DB for the current and
  adjacent day only. `ephemeral_id` MUST NOT be persisted (§7).
- On uninstall, Android deletes Keystore entries. The wrapped blob becomes
  permanently undecryptable. **This is intended.** See §2.4.

**iOS: DEFERRED, not cancelled** (decision 33). The equivalent is Keychain with
`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` — `AfterFirstUnlock` because
background derivation must work with the device locked, `ThisDeviceOnly` to keep
the key out of iCloud Keychain and encrypted backups. Written down now so it is
not re-derived later; **not measured, not implemented, not on the critical path.**

### 2.4 Reinstall, device change, and recovery — re-issue, never re-deliver

The tension a careful reader will spot: ADR-008 sells **recovery** as a benefit,
and M7 says the key is **never re-fetchable**. Both hold, because recovery does
not need the *same* key.

> **Rule: a device that has lost its `account_key` is issued a NEW one. The old
> key is never re-delivered to anyone, under any circumstance, including to its
> legitimate owner.** Recovery is a rotation event (§8), not a key retrieval.

This works because **account continuity does not require `account_key`
continuity.** Everything a user would grieve losing — the account, matches,
threads, message history, encounter history, entitlements — is keyed server-side
by account id, not by `account_key`. `account_key` is *only* the root of the BLE
broadcast identity. Rotating it changes what the device broadcasts tomorrow; it
changes nothing the user can see.

| Event | What happens |
|---|---|
| App reinstall, same device | Keystore wrap key gone ⇒ blob undecryptable ⇒ **re-issue (new `kid`)** |
| New device, old device retired | **re-issue (new `kid`)**; old key revoked at the seam (§8.4) |
| New device, old device still in use | See §9. Only one device advertises. |
| Factory reset / device lost | **re-issue (new `kid`)**; old key revoked |
| Suspected compromise | **emergency rotation** (§8.3) |

What re-issuance costs, stated so nobody is surprised:

1. **Peers must resync.** Resolution is against published `daily_key`s (§6.1).
   A peer that is online picks up the new keys on its next candidate-set sync
   and never notices. A peer that is offline continues holding your old daily
   keys and **cannot resolve you until it syncs.** Offline-only discovery of a
   just-recovered account does not work until one of the two devices reaches the
   network. This is a genuine hole in the offline moat, it is small, and it is
   honest to state it.
2. **Re-issuance MUST be rate-limited, audited, and notified to the account
   owner** — it is a security-relevant event. Unlimited self-serve re-issuance is
   a denial-of-discovery vector: an attacker who briefly controls a session can
   force re-issuance and make the victim's real device silently undiscoverable.
3. Re-issuance MUST NOT be silently triggered by a transient decryption failure.
   A Keystore read that fails once is a bug or a transient TEE fault, not a lost
   key. Retry, then require an explicit user-visible recovery action.

### 2.5 Revocation, and why it is not instant

Revoking a key means the server stops publishing that key's `daily_key`s, so
resolvers stop building table entries for it (§6.1). Consequences:

- A stolen device holding a revoked `account_key` keeps deriving valid-looking
  eids. **It becomes undiscoverable, not silent.** That is the correct failure
  mode: it is still emitting a properly rotating, unlinkable value, so it leaks
  nothing, and nobody resolves it.
- **Revocation propagates at candidate-set resync speed, not instantly.** A peer
  that has not synced since the revocation can still resolve the revoked device
  until it does. Bound: the resync interval, and at worst the resolution
  retention window (30 d, or 24 h free tier).
- Therefore revocation is **not** a safety control for blocking. Blocking is
  enforced by candidate-set absence at the resolving device (§6.1, invariant 7)
  and by the server refusing to publish, and it inherits the same propagation
  delay — which is why blocking must also be enforced at every online surface,
  not only at key resolution.

## 3. Rotation timing — synchronised, never staggered

Rotation happens at the **global UTC 15-minute boundary**: `:00`, `:15`, `:30`,
`:45`. Not on a per-device timer started at app launch.

**Do not add jitter to rotation timing.** This will be proposed — jittering
timers is usually good privacy hygiene, so the instinct is reasonable and wrong
here.

If every device rotates at the same instant, then at each boundary the entire
population changes identity simultaneously and an observer sees `N` IDs vanish
and `N` appear with no way to pair them. The anonymity set is the whole
population in range.

If devices rotate on individual staggered timers, each rotation is an isolated
event: one ID disappears and, moments later, one appears at the same signal
strength in the same place. Pairing them is trivial. Staggering converts a
population-sized anonymity set into an anonymity set of one, and every rotation
becomes a linkable hinge. The chain reassembles a permanent track from
"rotating" identifiers.

Synchronised rotation is strictly better. It is a load-bearing design property,
not an implementation convenience.

## 4. The MAC / RPA co-rotation rule

> **`ephemeral_id` and the BLE Resolvable Private Address rotate together.
> Both, or neither. There is no third option.**
> — safety invariant 5, owned by this document.

### 4.1 The attack when they desync

Suppose the ephemeral ID rotates at time `T` but the MAC rotates at `T + Δ`.
An observer logging `(MAC, eid, timestamp)` sees:

```
 t < T          (MAC_1, eid_1)
 T ≤ t < T+Δ    (MAC_1, eid_2)     ← MAC_1 bridges eid_1 → eid_2
 t ≥ T+Δ        (MAC_2, eid_2)     ← eid_2 bridges MAC_1 → MAC_2
```

`MAC_1` is observed alongside both `eid_1` and `eid_2`, so the observer knows
they are the same device. Then `eid_2` is observed alongside both `MAC_1` and
`MAC_2`, so those are the same device too. Repeat at the next boundary and the
next. **Every rotation becomes a link in a chain rather than a break in one**,
and the observer reconstructs a single unbroken pseudonymous identity for as
long as the device is in range — days, if they leave a Raspberry Pi in a café.

The same argument runs in reverse if the MAC rotates first. The direction of the
skew does not matter. **One un-rotated field defeats every other rotating
field.** This is why the two are specified as a single atomic control and not as
two independent settings, and why any change to either one is a review item on
the other.

`Δ` does not need to be large. A single overlapping observation is enough. A
`Δ` of one advertising interval — 250 ms — is sufficient to link, if an observer
happens to catch a packet in the window.

### 4.2 What implementations must do

Neither platform lets an application set the RPA directly. The strongest
available lever on both is a **full advertising restart**:

```
at each epoch boundary:
  1. stop advertising                     (release the advertising set entirely)
  2. derive ephemeral_id(d, e)            (new epoch)
  3. rebuild the advertisement payload
  4. start advertising                    (new advertising set)
```

Both stacks are *expected* to generate a fresh RPA when advertising restarts.
**"Expected" is doing a lot of work in that sentence and it has not been
verified.** See §5.

**Raised independently by android-kotlin and ios-swift, from opposite sides:
neither platform gives an application any control over RPA rotation.**

- **iOS.** `CoreBluetooth` neither exposes the local address nor accepts a
  rotation instruction. The app cannot read its own MAC, so it cannot even
  detect a desync locally.
- **Android.** No public API sets or reads the advertising address. The only
  lever is stop → start advertising, and **whether that produces a fresh RPA is
  chipset- and firmware-dependent.** The Bluetooth controller owns the address;
  the host stack requests, it does not command. Behaviour varies by OEM, by SoC
  vendor, and plausibly by firmware revision within a single model.

This is not a documentation question. Vendor documentation does not cover it and
where it does, it is not reliably accurate. **It needs a sniffer.**

Additional mandatory rules:

- All caches keyed by peer address MUST be cleared at the rotation boundary:
  connection quarantine lists (`SPEC.md` §7.4), Carrier B payload caches, peer
  handles. Keeping an address-keyed structure across a rotation reintroduces
  precisely the linkage the rotation exists to break — on our own side.
- The local peer identity handle exposed by `mobile/shared/protocol/` MUST be
  epoch-scoped. `CBPeripheral.identifier` on iOS and `BluetoothDevice` addresses
  on Android MUST NOT be persisted beyond the encounter record's own TTL, and
  MUST NOT be used as a database key.
- **Bonding is forbidden** (`SPEC.md` §7.3). A bond exchanges an IRK, which is a
  permanent key for resolving this device's RPA. Bonding defeats invariant 5
  completely and permanently, regardless of how correctly this schedule rotates.

### 4.3 Per-OEM co-rotation axis — B8. THE TOP TECHNICAL RISK IN THE PROJECT.

Under android-first (decision 33) Android is the entire product surface. An OEM
that cannot rotate its MAC is therefore **not a coverage gap — it is a hole in
the product.** This subsection is written to be executable by qa-test with no
further design input, because it is the first thing the rig should measure and
the only Phase 0 finding that cannot be designed around afterwards.

Because the behaviour lives in controller firmware, **invariant 5 is not a
per-platform property. It is a per-device-model property**, and it must be
measured as one. A single "Android works" result is not transferable to another
handset, and a result on one firmware revision is not transferable across an OTA.

#### 4.3.1 The exact question

Everything reduces to one binary question, and it is worth writing so precisely
that a capture either answers it or does not:

> Over a capture window spanning ≥6 consecutive epoch boundaries, is the mapping
> between observed advertiser addresses and observed `ephemeral_id`s a
> **bijection**?

That is, no `AdvA` is ever seen with two different eids, and no eid is ever seen
with two different `AdvA`s. A bijection means every rotation is a clean break. A
single violation in either direction is the §4.1 bridging attack, and one packet
is enough (§4.1) — **there is no "mostly passes".**

This formulation is deliberately checkable by a script over a pcap, with no
device-side instrumentation at all: the eid is in the Service Data of the same
PDU that carries the advertiser address, so the capture is self-contained.

#### 4.3.2 The pre-test that costs one packet

Before any 90-minute run, read the **advertiser address type** from a single
captured PDU. The two MSBs of the most significant address byte:

```
0b01 xxxxxx   Resolvable Private Address    ← the only acceptable value
0b11 xxxxxx   Static random                 ← FAIL. stable for the boot session, often longer.
0b00 xxxxxx   Non-resolvable private        ← rotates, but see note below
(TxAdd=0)     Public device address         ← CATASTROPHIC FAIL. globally unique, permanent.
```

A public or static-random advertiser address is a **permanent on-air identifier
that we did not put there and cannot remove**. It defeats invariant 5 more
completely than a slow RPA does, and it makes the 15-minute eid rotation
decorative. **One packet settles it. Run this screening test on every model
before spending 90 minutes on it.**

(Non-resolvable private addresses rotate and are acceptable for our purpose —
we never need a peer to *resolve* our address, since we forbid bonding, §7.3.
If a controller emits NRPAs that rotate on our restart, the bijection test is
what matters and the address type is not disqualifying. Record it either way.)

#### 4.3.3 The measurement table

Populate one row per (model, OS build) on the rig. Every cell starts UNMEASURED
and may only be filled from external sniffer capture (§5).

| Model | SoC / BT controller | OS build | addr type (§4.3.2) | fg bijection | bg bijection | observed RPA period | phase vs our boundary | verdict |
|---|---|---|---|---|---|---|---|---|
| _(Android, per OEM+SoC — FIRST-CLASS, on the critical path)_ | — | — | UNMEASURED | UNMEASURED | UNMEASURED | UNMEASURED | UNMEASURED | — |
| _(iPhone, per generation)_ | — | — | **DEFERRED** | **DEFERRED** | **DEFERRED** | **DEFERRED** | **DEFERRED** | **DEFERRED** |

`DEFERRED` = deliberately not scheduled under decision 33. It is **not** an
unknown risk on the current plan and MUST NOT be counted as one in the go/no-go.
It becomes UNMEASURED again the moment iOS returns to scope.

**Minimum Android sample.** Two physical units per (OEM, SoC) pair, because
per-unit firmware variation within a model is possible and a single unit cannot
distinguish "this model" from "this handset". Cover, in this order:

1. **MediaTek-based budget devices (Transsion/Infinix/Tecno, Realme, low-tier
   Xiaomi).** Highest risk, least documented BT controllers, and a large share
   of the install base in our target markets. **These belong in the first batch,
   not the second.** The instinct to test flagships first is exactly backwards:
   flagships are the devices most likely to pass.
2. Samsung — both Exynos and Snapdragon variants of the same model name. They
   are different controllers wearing the same marketing name.
3. Xiaomi / Oppo / Vivo mid-tier (Snapdragon).
4. Google Pixel (Tensor) — the reference behaviour, useful as a control, least
   representative of the install base.

#### 4.3.4 Verdicts and the decision rule for each

| Verdict | Observation | Decision rule — pre-decided, not a discussion |
|---|---|---|
| `NOT-RPA` | Address type public or static-random (§4.3.2) | **Model excluded from advertising. Ships scan-only. No product discussion, no exception.** A permanent on-air MAC is a tracking beacon regardless of what our payload does. |
| `CO-ROTATES` | Bijection holds, all boundaries, fg **and** bg | Ship advertising. Record the OS build; re-test after any OTA touching the BT stack. |
| `CO-ROTATES-FG-ONLY` | Bijection holds fg, fails bg | Advertise in foreground only on this model. Background = scan-only. Product copy MUST NOT promise background presence on it (`SPEC.md` §5.4 Tier 3 framing). |
| `SLOWER` | `AdvA` rotates on its own period P > 15 min; eids cluster in groups of ⌈P/15⌉ per address | §4.4: lengthen the eid epoch to P. **See §4.3.5 — this is a GLOBAL change, not a per-model one, and that is the non-obvious part.** |
| `PHASE-OFFSET` | `AdvA` rotates with period ≈15 min but **not at our boundary** (constant offset Δ) | Bijection fails on every boundary by Δ. If `stop→start` forces an immediate fresh address, the restart resets phase and the verdict upgrades to `CO-ROTATES` — **test that explicitly.** If it does not, we cannot fix it in software: we cannot read our own address, we cannot set it, and we cannot align our epoch to a per-device phase without destroying global rotation synchronisation (§3). Treat as `NO-ROTATION`. |
| `NO-ROTATION` | `AdvA` constant across boundaries while advertising is active | §4.4: exclude the model, or ship it scan-only. **Never rotate the payload against a fixed MAC and call it rotation.** |
| `INCONSISTENT` | Different results across firmware builds or between the two units of a model | Take the **worst** observed result for the model, and add OS build as a table dimension. Do not average, do not take the best. |

**`PHASE-OFFSET` is the outcome I expect people to be least prepared for, and it
is not exotic.** The Bluetooth spec's default RPA timeout is 900 seconds — the
same 15 minutes as our epoch. Same period, different phase, is the most likely
"it rotates fine!" result from a careless test, and it is a **permanent** bridge:
every single boundary leaks the link, forever, for as long as the device is
observed. A test that only checks "does the address change at all, and how
often" will report success here. The bijection test in §4.3.1 catches it; a
period-only test does not. This is the specific reason §4.3.1 is phrased as a
bijection and not as "the address changes every 15 minutes".

#### 4.3.5 A per-model `SLOWER` result forces a GLOBAL epoch change

Non-obvious and load-bearing, so it is stated separately.

§3 requires that **the entire population rotates at the same instant.** That
means the epoch length is a single global protocol constant. There is no such
thing as a per-model epoch — a device rotating on a different schedule from
everyone else is a population of one at every boundary, which is the exact
failure §3 exists to prevent, and it is *worse* than rotating slowly.

Therefore, if any model we intend to ship comes back `SLOWER` with period P:

- either the **global** epoch lengthens to P for every device on every platform,
- or that model is excluded / shipped scan-only.

There is no third option, and in particular there is no "give that model a
45-minute epoch". Decision rule: set the global epoch to the slowest period P
among models we intend to ship advertising on, **capped at 60 minutes**. Beyond
an hour, a café visit, a commute, or a workplace lunch sits entirely inside one
identity and rotation has stopped defeating the intermittent observer it exists
to defeat; a model requiring P > 60 min is treated as `NO-ROTATION`.

#### 4.3.6 Aggregate go/no-go rule

Individual verdicts are compatibility notes. The **distribution** is a go/no-go
input, and it needs a threshold agreed before the data arrives, so that the
threshold is not chosen to fit the result:

- Express results as a share of the **intended install base in the launch
  market**, not as a count of models tested.
- **Proposed threshold: if models verdicted `CO-ROTATES` (or `CO-ROTATES-FG-ONLY`)
  cover less than 80 % of the intended install base, this is escalated as a
  go/no-go question, not filed as a compatibility note.** The number is mine to
  propose and the founder's to set; what matters is that it is set *before* the
  measurement, and it is written here so it can be checked afterwards.
- **Any model shipped scan-only MUST tell its user so, in the Radar UI, in plain
  language.** "This phone can see people nearby but cannot be seen by them"
  is a sentence a user is entitled to, and quietly shipping a device that can
  never be discovered is the kind of omission `CLAUDE.md` bans elsewhere under
  dark patterns. This is a product requirement that falls out of a protocol
  measurement, and it should be designed before the measurement returns, not
  after.
- The named excluded/scan-only model list is a public support-doc artifact, not
  an internal note.

A `NO-ROTATION` or `NOT-RPA` model is not a device we can make safe by changing
our code. The escalation path is `SPEC.md` §11.

### 4.4 If the platform will not co-rotate

Two failure shapes, with pre-decided answers:

- **MAC rotates more slowly than the eid** (e.g. the OS holds an RPA for 45
  minutes while we rotate the eid every 15). Then the eid rotation is not
  buying what it claims. The correct response is to **lengthen the eid rotation
  to match the observed MAC period** — never to declare the mismatch acceptable.
  Slower rotation with co-rotation is strictly more private than faster rotation
  without it.
- **MAC does not rotate at all while advertising is active.** Then invariant 5
  is unenforceable on that device and the privacy architecture does not hold
  there. That is a stop-and-escalate, not a work-around. See `SPEC.md` §11.
  The options are all bad and all better than shipping it silently: exclude the
  model, or ship it with advertising disabled (scan-only, "see but not seen" —
  the device can still discover, it simply cannot be discovered), or do not ship
  on that hardware. **What we do not do is rotate the payload against a fixed
  MAC and call it rotation.** That is worse than no rotation, because it looks
  like a privacy feature in code review and in the marketing copy while
  providing none.

### 4.5 What rotation does *not* protect against

Stated plainly, because rotation is frequently oversold.

Rotation defeats an **intermittent or distributed** observer: someone who sees
you in a café on Monday and a station on Thursday cannot connect the two.

Rotation does **not** defeat a **continuous co-located** observer. Someone
following you with a scanner sees an unbroken RSSI trajectory across the
rotation boundary and simply re-acquires. No identifier scheme fixes physical
tailing. Residual on-air fingerprints — `tx_power_cal` class (~2.8 bits, by
design), `CONNECTABLE = 0` (~1 bit) — reduce the boundary anonymity set further
but are dominated by signal-continuity linkage anyway.

We should say this honestly in any external privacy write-up. Claiming rotation
defeats stalking would be false, and a survivor relying on that claim is exactly
the person we cannot afford to mislead.

## 5. Verification requirement — external sniffer, real hardware

**None of §4 is verifiable from inside the app.** iOS does not expose its own
MAC to `CoreBluetooth`; Android's advertiser does not report the address in use.
An implementation cannot self-test invariant 5.

Therefore the following is mandatory in the Phase 0 spike and handed to qa-test.
It is written to be executable without further design input, because under
android-first it is the **first** thing the rig should measure (B8, decision 33).

### 5.1 Sniffer hardware — what is actually needed, and the trap in the cheap option

| Option | Cost | Verdict |
|---|---|---|
| **3 × nRF52840 dongle** + nRF Sniffer for Bluetooth LE → Wireshark, **one dongle pinned to each primary advertising channel (37, 38, 39)**, captures merged by timestamp | ~£30 total | **RECOMMENDED.** Full primary-channel coverage, removes the false-negative below. |
| 1 × nRF52840 dongle | ~£10 | **NOT SUFFICIENT ALONE.** See the trap. Usable only for the §4.3.2 one-packet address-type screen. |
| TI CC1352 (CatSniffer / Sonoff) + Sniffle | ~£25 | Acceptable alternative; confirm all-three-advertising-channel coverage before trusting a negative result. |
| Ellisys Bluetooth Tracker/Vanguard, Teledyne Sodera | £thousands | All-channel, timestamped, ideal. Not necessary for this question. Do not let procurement lead time become the blocker. |

**The trap, and it is the reason to buy three dongles instead of one.** A
single-channel sniffer sees roughly one third of advertising events. The
measurement we are making is an assertion of **absence** — that no packet ever
carries an old address alongside a new eid. A missed packet and an absent packet
are indistinguishable in a single-channel capture, so **a single-channel "no
overlap observed" result is not evidence of no overlap.** It is the cheapest
possible way to record a false pass on the highest-severity question in the
protocol. Three dongles cost £30 and remove the ambiguity.

Nothing else is required. No device-side instrumentation, no debug build, no
rooted phone: the eid travels in the Service Data of the same PDU that carries
the advertiser address, so `(t, AdvA, AdvA_type, eid)` comes out of the capture
alone. Filter in Wireshark on the 16-bit service UUID (`SPEC.md` §4.1) to
exclude unrelated BLE traffic.

### 5.2 Capture protocol

Per device model, per condition:

1. Run the §4.3.2 **address-type screen** first. One packet. If it fails, stop —
   the model is `NOT-RPA` and no further capture is needed.
2. Device advertises Carrier A (`SPEC.md` §5.1) on the real 15-minute UTC epoch
   schedule. **Do not use a compressed test epoch.** The question includes the
   interaction between our boundary and the controller's own ~900 s RPA timer
   (§4.3.4 `PHASE-OFFSET`); shortening our period changes the thing being
   measured.
3. Capture ≥ **90 minutes**, spanning ≥ 6 consecutive epoch boundaries.
4. Conditions, each captured separately: **fg screen-on · fg screen-off ·
   background under a foreground service · after Doze entry · after a Bluetooth
   stack restart (BT off/on)**. The last two are where OEM power management is
   most likely to change controller behaviour.
5. Re-run after any OS update that touches the Bluetooth stack.

### 5.3 Pass criterion — assertable over the pcap

Let `P` = all captured PDUs matching our service UUID, as `(t, AdvA, AdvA_type, eid)`.

```
PASS iff all of:
  C1  every AdvA_type is resolvable-random (0b01) or non-resolvable-private (0b00)   §4.3.2
  C2  the relation eid <-> AdvA over P is a BIJECTION                                §4.3.1
        no eid appears with 2 distinct AdvA
        no AdvA appears with 2 distinct eid
  C3  >= 6 distinct eid values observed (proves >= 6 boundaries were spanned)
  C4  COVERAGE: >= 1 packet captured in the last 5 s before, and the first 5 s
      after, EVERY boundary in the window
  C5  capture yield >= 60 % of expected packet count
        expected ~= window_seconds / advertising_interval, across 3 channels
```

`C4` and `C5` are not bureaucracy. Without them, `C2` passing is
indistinguishable from `C2` being untested at the only instants that matter —
the boundaries. **A capture that fails `C4` or `C5` is VOID, not a pass and not a
fail.** Record it as void and re-run.

Also record, even on a clean pass: the observed RPA period, and its phase
relative to our boundary. If the controller rotates on its own schedule *as well*
as on our restart, the interaction between its period and our epoch must be
understood rather than assumed — that is where `PHASE-OFFSET` hides.

### 5.4 What this measurement cannot be replaced by

**A simulator cannot produce this measurement. Neither can a device without an
external sniffer. Neither can a green conformance-vector run** — the vectors in
`vectors/` prove arithmetic and nothing else, and they are silent on every
question in this section. Any claim that invariant 5 holds, made without sniffer
capture meeting §5.3, is not evidence and MUST NOT be recorded as a pass.

**Nothing in this document has been hardware-validated.** It was written at a
desk with no JDK, no Mac, no handsets, and no sniffer. Every §4.3 cell is
UNMEASURED or DEFERRED, and that is the true state of the world as of
2026-08-04.

This is the highest-severity open question in the protocol (`SPEC.md` §11) and,
under android-first, the highest-severity technical risk in the project (B8).

## 6. Resolution, clock skew, and the replay window

### 6.1 Resolution

A receiver holds a candidate set of `daily_key`s for people it may plausibly
meet — matches, likes, and for Open mode a bloom filter of active nearby-region
users synced when last online.

Resolution MUST be a precomputed table lookup, not a per-observation scan:

```
once per epoch:
  table = { ephemeral_id(d, e') : (candidate, e')
            for candidate in candidate_set
            for e' in accepted_epoch_window }
per observation:
  look up the observed eid in table          O(1)
```

For 500 candidates and a ±1 epoch window that is 1500 HKDF operations per
15 minutes — negligible — versus 1500 per *advertisement* if done naively.

**Candidates rotate too (v0.1).** A candidate's `daily_key` for a given day may
come from a different `kid` than the day before, or even than the epoch before
(§8.3, EMERGENCY). The table is built **once per epoch**, so this costs nothing
extra — the resolver simply uses whichever published `daily_key` covers
`(candidate, day, epoch)`. What it forbids is caching a candidate's key across
epochs on the assumption that a day maps to one key. It does not. If a candidate
rotated mid-day, the day has two.

**Two rules that are safety controls, not optimisations:**

- A blocked account's `daily_key` MUST NOT be in the candidate set. Blocking is
  enforced by *absence of the key*, so a blocked person is not merely hidden —
  they are cryptographically unresolvable and no peer instance is ever created
  (invariant 7).
- Open-mode bloom-filter hits MUST be re-checked against the exact local
  blocklist before resolving. A bloom filter has false positives; a false
  positive that resolved a blocked person would be a safety incident, not a
  glitch.

An unresolvable frame MUST be dropped entirely. It MUST NOT be surfaced as an
anonymous blip or counted in any user-visible "people nearby" figure. Doing so
would leak the presence of people the user is not permitted to see — including
people who blocked them — and would let anyone census Radius users in a space.

### 6.2 Clock skew

Devices drift. A device whose clock is wrong derives the wrong epoch and becomes
undiscoverable.

- Receivers MUST accept `e-1`, `e`, `e+1` — a **±1 epoch window**.
- If the device has not synchronised time in over 7 days, it MAY widen to ±2.
- It MUST NOT widen further. Beyond ±2 the replay window (§6.3) becomes the
  dominant risk.
- Devices SHOULD maintain a monotonic-clock-corrected time reference established
  at last server contact, rather than trusting wall-clock alone.
- Frames MUST NOT be rejected for epoch reasons alone; only failure to resolve
  against the whole accepted window is a non-match.
- **The window is over epochs, and each epoch is derived under the `kid` active
  at that epoch** (§8.4). At a rotation seam the window legitimately spans two
  keys. This neither widens the window nor creates a second identity in any
  single epoch.

### 6.3 The replay window is the skew window

These are the same number and the trade is one-for-one:

```
±1 epoch  →  a captured ephemeral_id replays successfully for up to 30 minutes
±2 epochs →  up to 60 minutes
```

An attacker who captures an ephemeral ID can rebroadcast it within that window
and make a victim's device believe that person is nearby.

What replay achieves: **false presence, and nothing else.** The attacker cannot
wave, cannot complete a handshake, cannot open a session, and cannot impersonate
consent — all of those require signatures verified against an identity key the
attacker does not hold (`SPEC.md` §3.4, `STATE_MACHINE.md` §5).

What false presence is still good for, and why we care: making a target believe
a specific person is at a specific place. That is a plausible harassment or
luring vector. It is bounded by the window, which is the argument for keeping the
window at ±1 wherever possible.

Mitigation available without protocol change: a resolved peer whose signal
appears without a plausible approach trajectory — full-strength on first sight,
no ramp — is anomalous, and the UI SHOULD NOT escalate to "HERE" on a single
epoch of observation. `BANDING.md`'s warm-up and hysteresis rules already
provide most of this incidentally.

## 7. Key lifetime and deletion

| Key | Lifetime | Storage — DEVICE | Storage — SERVER | On account delete |
|---|---|---|---|---|
| `account_key` (active `kid`) | until rotation or account deletion | AES-GCM blob wrapped by a non-exportable Keystore key (§2.3). **Not hardware-held — see §2.3.** | **retained**, own table, DEK in OpenBao (ADR-008 M1/M2) | Keystore entry destroyed; server row + backups destroyed at end of 30-day grace (M5) |
| `account_key` (superseded `kid`) | **destroyed on the device at the seam** (§8.5) | MUST NOT be retained after its successor becomes active | retained per M1/M5 policy | as above |
| `account_key` (pending `kid`) | from receipt until `effective_from` | same wrapping as active | retained | as above |
| `daily_key` (own) | 24 h; retained for the resolution window only | encrypted local DB (SQLCipher) | derivable from `account_key`; published to candidates | hard-deleted |
| `ephemeral_id` | 15 min | derived on demand, **never persisted** | never stored | n/a |
| candidate `daily_key`s (peers) | resolution window: 30 d, or 24 h free tier | encrypted local DB | published per day per candidate | hard-deleted |

**The `account_key` row is the one that changed under ADR-008**, and it changed
in two ways that matter: there is now a server column, and the device column is
weaker than the previous text implied. The old table said "hardware-backed where
available, non-exportable". That was aspirational and, for this schedule, not
achievable — §2.3 explains why HKDF-Extract cannot run on a non-exportable
Keystore key, and what we get instead.

`ephemeral_id` values MUST NOT be persisted. They are derivable in O(1) from the
daily key, so storing them buys nothing and creates a durable log of exactly the
identifiers the design exists to make ephemeral.

Encounter records MUST NOT store the raw `ephemeral_id`, the peer's MAC, or a
timestamp finer than the epoch. An encounter is *(account, band, epoch)* and
never a location (glossary: "encounter — record that 2 accounts shared a
band+time. NEVER a location").

## 8. `account_key` rotation — the key ring and the seam (ADR-008 M4)

**Vectors:** `vectors/key_rotation.json`.

M4 requires that `account_key` be rotatable and that rotation be tested. This
section is the protocol that makes it so. It is new in v0.1; the previous spec
had no rotation concept because a device-generated key never needed one.

### 8.1 What rotation does and does not do

Rotation invalidates **future** derivation only. It bounds forward exposure. It
does **not** undo past exposure, and it must never be described as doing so —
internally, in support copy, or externally (M4, verbatim). An observer or
operator holding a superseded `account_key` and an old BLE capture can still
derive every eid that key ever produced. That is permanent.

### 8.2 The key ring

A device holds an ordered **key ring**, not a key:

```
KeyRingEntry = { kid: uint32, account_key: bytes[32], eff_day: uint32, eff_epoch: uint16 }
KeyRing      = non-empty list of KeyRingEntry

active(ring, d, e) = the entry with the greatest (eff_day, eff_epoch)
                     such that (eff_day, eff_epoch) <= (d, e)      lexicographic order
```

Validation, performed once when a ring is loaded or updated:

| Condition | Error |
|---|---|
| `eff_epoch` outside `0..95` | `E_EPOCH_INDEX_OUT_OF_RANGE` |
| two entries share the same `(eff_day, eff_epoch)` | `E_KEY_RING_NOT_MONOTONIC` |
| `kid` order does not agree with `(eff_day, eff_epoch)` order | `E_KEY_RING_NOT_MONOTONIC` |
| `account_key` not exactly 32 bytes | `E_ACCOUNT_KEY_LENGTH` |
| ring is empty, or no entry is effective at the queried `(d, e)` | `E_NO_ACTIVE_KEY` |

`kid` is a monotonically increasing key id starting at 0. It is bookkeeping,
never transmitted, never derived from, and **never on the air**.

**`effective_from` is expressed as an epoch index. Mid-epoch is not
representable.** That is the design: the illegal state is unconstructible rather
than merely forbidden. A rotation that took effect part-way through an epoch
would be a *staggered* rotation, which §3 rejects — one device changing identity
at an instant when nobody else does is an anonymity set of one, and the change
is a trivially linkable hinge. Rotation must hide inside the population-wide
boundary, and the only way to guarantee that is to make off-boundary rotation
inexpressible.

### 8.3 Two rotation classes

| Class | Trigger | `eff_epoch` | Lead time |
|---|---|---|---|
| **SCHEDULED** | reinstall, device change, recovery, routine cadence, M4 exercise | **MUST be 0** — i.e. a UTC **day** boundary | next day boundary |
| **EMERGENCY** | suspected key compromise, breach response | MAY be any `0..95` — the next 15-minute boundary that gives the device time to receive it | ≥ 1 epoch, **≥ 2 epochs recommended** |

SCHEDULED lands on a day boundary because `daily_key` is the publication unit
(§6.1). A day-boundary rotation means **no day ever has two daily keys for one
device**, so the resolver's table build is trivially correct and the rotation is
completely invisible in the resolution path — it looks exactly like the daily
key change that happens every midnight anyway.

EMERGENCY accepts the extra complexity (one day carrying two `kid`s for one
device) in exchange for acting within 30 minutes instead of within 24 hours.
That is the right trade for a compromise and the wrong one for a reinstall.

**Server issuance rule:** `effective_from` MUST be strictly in the future at the
moment of issuance, by at least one full epoch.

**Client validation rule — deliberately asymmetric:** a client MUST accept a ring
entry whose `effective_from` is already in the past. That is the normal state for
a device returning from a week offline. **Do not add a client-side "must be in
the future" check.** It would brick exactly the devices that most need to catch
up, and it is the kind of symmetric-looking validation that gets added in review
by someone who has not read this paragraph.

### 8.4 The seam — exactly what happens, stated as the two things that must not happen

> **At any `(d, e)` there is exactly one active `kid`, therefore exactly one
> valid `ephemeral_id` per device per epoch. Neither a gap nor a duplicate is
> representable.**

*No duplicate.* `active()` returns the entry with the **greatest** effective
boundary not after `(d, e)`. On a validated ring the effective boundaries form a
strict total order, so "greatest" is unique. Two keys cannot both be active.

*No gap.* `active()` is total over every `(d, e)` at or after the ring's first
entry. `kid = 0` is issued with `effective_from = (0, 0)`, so from the account's
first epoch onward there is always an active key. A query before the ring's first
entry returns `E_NO_ACTIVE_KEY` — a fault, not a silent empty result.

*The transmitter* derives and broadcasts the eid for the current epoch under the
currently active `kid`, and nothing else. It never emits two eids, never emits a
superseded one, and does nothing special at the boundary beyond the normal
advertising restart of §4.2.

**The one subtlety, and the answer.** The receiver's ±1 skew window (§6.2)
straddles the seam. At `e = eff_epoch` the accepted window is `{e-1, e, e+1}`,
and `e-1` is under the *old* `kid` while `e` and `e+1` are under the *new* one:

```
epoch:      eff-2      eff-1   |   eff       eff+1
kid:        kid_old    kid_old | kid_new    kid_new
                               ^ the seam
```

**This is not two identities in one epoch. It is one identity per epoch, over a
window that happens to straddle a seam.** The resolver builds its table per
epoch and derives each epoch under the `kid` active *at that epoch* — which is
what `active(ring, d, e')` already returns for each `e'` in the window, with no
special case. The rule is simply: *evaluate the ring per epoch, not once per
table build.* An implementation that resolves `kid` once and reuses it across the
whole window produces a gap at exactly one epoch per rotation, per user, and will
pass every test that does not straddle a seam. `vectors/key_rotation.json`
straddles seams on purpose.

The replay window is unaffected: it is still the skew window (§6.3), still ±1
epoch, still 30 minutes. Rotation neither widens nor narrows it.

### 8.5 Device obligations at the seam

1. At the boundary, the device performs the normal §4.2 advertising restart. The
   restart is identical whether or not a rotation occurred. **A rotation MUST NOT
   be observable as a change in radio behaviour** — no extra restart, no timing
   change, no gap in advertising, no reconnect.
2. **The superseded `account_key` is destroyed on the device at the seam.** The
   ring retains the entry's `kid` and `effective_from` for ordering, and zeroes
   the key material. A device holds at most one active key and one pending key.

   *Precise rule:* destroy every entry **strictly older than the entry active at
   the current `(d, e)`**. Not "the previous one" — a key that was active for a
   single epoch between two rotations is superseded too. The active entry and any
   pending entry are never destroyed, which is what makes this safe to drive from
   the device's own clock: a clock that runs fast destroys only history it was
   required to destroy anyway and never stops the device advertising. Nothing is
   destroyed when the ring does not validate, or when the queried instant is
   before the ring's first entry — destruction is irreversible, and it must not
   act on input we have just declared untrustworthy or on a rewound clock.

   *A destroyed entry resolves to `E_NO_ACTIVE_KEY`*, the same fault as a query
   before the ring began, because from the resolver's side they are the same
   state: no key here. It MUST NOT derive from the zeroed bytes — that would
   produce a valid-looking, wrong, and identical-for-every-pruned-device
   identifier.

   *What this is worth, and what it is not.* §2.3 is explicit that the Keystore
   wrap gives no protection against a compromised running process or a rooted
   device: HKDF-Extract needs the raw key in memory. Retaining every key ever
   issued therefore means one in-process compromise yields **retroactive**
   derivation across the device's whole rotation history — the exact blast radius
   §8.1 says rotation exists to bound. Destroying at the seam is what makes §8.1's
   "rotation bounds future exposure" true on the client instead of aspirational.
   It is **best effort at the memory level**: `fill(0)` overwrites the buffer we
   hold, and a moving garbage collector may already have copied it somewhere we
   cannot name. The property the protocol can honestly state is *the derivation is
   gone*, and that is what `vectors/key_rotation.json → destruction_at_seam`
   proves — the same `(d, e)` yields its known eid before the prune and
   `E_NO_ACTIVE_KEY` after it.

   *Interaction with §9.6, stated rather than discovered.* The accepted window is
   `{e-1, e, e+1}`, and at a seam `e-1` belongs to the key just destroyed. So for
   one epoch after a rotation a device cannot re-derive, and therefore cannot
   recognise, its own previous-epoch `ephemeral_id`: a reflected or relayed copy
   of it is passed to resolution instead of being dropped by §9.6. In practice it
   then fails to resolve, because a device does not carry its own account among
   its resolution candidates — but §9.6 exists precisely so that the outcome does
   not *depend* on that, so the loss is real and is stated rather than explained
   away. **This is accepted deliberately.** §9.6 self-rejection is defence in depth against a rare
   event (reflection, a relay, a twin device); destruction at the seam is a
   normative rule against a permanent exposure. Holding the superseded key 15
   minutes longer to keep a duplicate-broadcast detector alive would spend exactly
   the property the destruction buys, and would mean the old key is still present
   during every rotation — the one moment it is most worth not having. Pinned by
   the `self-eid-rejection-loses-the-previous-epoch-after-a-seam-prune` vector so
   that a future reader meets it as a decision rather than as a surprise.
3. All caches keyed by peer address are already cleared at every boundary (§4.2).
   Nothing additional is required at a seam — which is the point.
4. Own `daily_key`s derived from the superseded key are deleted at the seam.
   Peers' candidate keys are unaffected: they belong to other accounts' rings.

### 8.6 If a device misses a rotation

A device that has not received the new `kid` by its effective boundary continues
with the newest key it holds.

- **It becomes undiscoverable. It does not become insecure.** It is still
  emitting a properly rotating, unlinkable value that no resolver accepts. This
  is the correct failure direction and it is worth designing for deliberately:
  **privacy behaviour must never depend on server reachability.**
- It MUST continue advertising, not stop. Stopping would be a distinguishable
  behaviour, and it buys nothing — the device is equally undiscoverable either
  way.
- It MUST attempt ring resync at the next connectivity.
- If it has been unable to resync for **> 7 days**, it SHOULD tell the user that
  Radar discoverability may be degraded. This is the same 7-day threshold that
  permits widening the skew window to ±2 (§6.2); a device that far out of contact
  is in a degraded state on both axes and the user should know.

### 8.7 Cadence — and the honest limit of routine rotation

**Routine rotation defends against a snapshot, not against persistent access.**
An attacker who exfiltrated the key table once loses coverage of everything
issued after the next rotation. An attacker with ongoing access to the key table
receives the new keys along with everything else. Rotation is therefore worth
much less against the breach scenario than it intuitively sounds, and it must not
be presented as the answer to it.

The load-bearing cases are **rotation on event**: reinstall, device change,
recovery, suspected compromise (§2.4).

Routine cadence: **90 days is proposed as the default.** The number is not the
protocol's to fix — this document specifies the seam, not the schedule — and it
belongs to security-privacy. Its cost is real: every rotation republishes daily
keys to every candidate, and any peer that fails to resync loses the ability to
discover you until it does (§2.4). A short cadence buys little and degrades
offline discovery for everyone.

**M4 testing obligation.** Rotation is exercised in CI by `key_rotation.json` at
the arithmetic level, and MUST additionally be exercised end-to-end at least once
per release against a staging server, including an EMERGENCY mid-day rotation.
The protocol-level property to assert is: **a device that has never rotated and a
device that has rotated twice are indistinguishable on air.**

### 8.8 What a third-party observer sees at a rotation

Nothing. At the boundary the device's eid changes, as it does at every boundary,
to another uniformly distributed 16-byte value, at the same instant as the entire
population (§3). The `kid` is not on air. `effective_from` is not on air. The
advertising restart is the same restart that happens at every boundary. **A root
key rotation is not observable from outside the device**, and this is a required
property, not a happy accident — a rotation that were observable would be a
per-device event at a moment when it is the only such event, i.e. §3's forbidden
staggered rotation wearing a different hat.

## 9. Multi-device — a new hazard introduced by ADR-008

> **Read this section first if you are reviewing ADR-008's consequences.** It is
> the place where server-issued keys bite hardest, and the bite is not in the
> operator threat model that ADR-008 discusses at length — it is in the
> third-party threat model that ADR-008 says is unchanged.

### 9.1 The problem in one sentence

Two devices holding the same `account_key` derive the same `daily_key` and
therefore **broadcast a byte-identical `ephemeral_id`, at the same instant, from
two different physical locations.** Under device-generated keys this could not
happen. Under ADR-008 it happens by default, and multi-device is one of the
benefits ADR-008 was bought for.

### 9.2 Why this is not a nuisance — it is invariant 5 defeated by another route

Five distinct harms, in descending order of how much they should worry you.

**(a) The fixed-location oracle. This is the one that ends up in a news story.**
A second device that sits still — a tablet at home, a phone on a desk at work —
broadcasts the account's *current* eid continuously from a known address.
Anyone able to observe that one location reads the account's live eid, every
epoch, indefinitely, from a parked car or a neighbouring flat. That eid then
identifies the user's **phone**, anywhere, for the remainder of the epoch plus
the ±1 window. A rotating identifier has been converted into a
**remotely-queryable live tracking token keyed to the victim's home address**,
available to an attacker who never has to follow anyone. This is a targeted
stalking primitive, and targeted stalking is the first entry in the abuse model.

**(b) Cross-device MAC bridging — §4.1, but structural and permanent.** Two
devices cannot share an RPA. An observer sees `(MAC_A, eid_X)` and
`(MAC_B, eid_X)` and learns that `MAC_A` and `MAC_B` are the same account. At the
next boundary both become `eid_Y`, and `MAC_A'` and `MAC_B'` are linked again.
The chain never breaks, at any boundary, ever. This is precisely the bridging
attack §4.1 exists to prevent — except that §4.1's version is a firmware accident
we might get lucky on, and this version is guaranteed by construction. It also
leaks something §4.1 does not: that these two devices belong to one person.

**(c) Anonymity-set collapse in the other direction.** Rotation works because the
whole population changes at once, leaving an observer no way to pair a
disappearance with an appearance (§3). A duplicated eid needs no pairing
inference at all — it is **self-pairing across space**. Two points on a map are
identified as one account directly, with certainty, from a single packet at each.

**(d) Replay becomes undetectable.** The same eid observed in two places at once
is the exact signature of the replay attack in §6.3. Once a legitimate account
can do it, we permanently lose the ability to distinguish "someone is replaying
you" from "your tablet is at home". A detection capability we could otherwise
have had is gone, and it is gone for every user, not only multi-device ones.

**(e) Banding is corrupted — a correctness bug on top of the privacy bug.**
`BANDING.md` assumes one physical emitter per resolved identity. Two emitters in
range feed one Kalman filter with two interleaved distance streams. The output is
not the distance to either device; it is an artefact. Invariant 2 delivers a
confidently wrong answer, which is the failure direction `SPEC.md` §5.0-b already
identifies as the one that matters.

### 9.3 The v0 answer — one advertising device per account

> **In v0, exactly one device per account may advertise. Every additional device
> operates SCAN-ONLY: it can discover, it cannot be discovered.**

- At enrolment the server assigns exactly one device the `ADVERTISE` role. Every
  other device receives `SCAN_ONLY`. The role is delivered alongside issuance
  (§2.2) and cached with the key ring.
- **Fail closed.** A device that has never been granted `ADVERTISE` MUST NOT
  advertise, including while offline, including on first run, including in debug
  builds.
- **Role transfer is an explicit user action** ("use Radar on this phone"),
  atomic server-side. Ordering is normative: the losing device stops advertising
  **immediately** on receipt; the gaining device starts advertising **at the next
  epoch boundary**. This guarantees the two never emit the same eid, even for one
  advertising interval. A disappearance mid-epoch is unremarkable (devices leave
  range constantly); an appearance at a boundary is unremarkable (everyone
  changes identity there). A hand-off *within* an epoch would be neither.
- A `SCAN_ONLY` device under Carrier A is fully passive and emits nothing
  (`SPEC.md` §5.5). Under Carrier B it must transmit to connect — which is
  another reason Carrier B is expensive, and is deferred with iOS anyway.

**Honest limit of this control.** It is a client rule plus a server-side role
assignment. It is **not** cryptographically enforced, and under a shared root it
cannot be: nothing stops a modified client from advertising. The threat being
managed is *accidental* duplication — a user installing on a phone and a tablet —
which is the realistic case and the one that produces §9.2(a) without anyone
intending harm. A user who modifies their own client to broadcast from two
devices degrades only their own anonymity. Do not mistake this for a security
boundary; it is a correctness control with a safety consequence.

### 9.4 What ADR-008 bought, precisely — and what it did not

ADR-008 lists multi-device as a benefit of server issuance. That benefit is
**real for account access and unreal for Radar broadcast**, and the distinction
was not drawn in the ADR:

| Capability on N devices | Status |
|---|---|
| Discover, Threads, chat, calls, entitlements, history | **works, unaffected, N devices** |
| Scanning / discovering others on Radar | **works, unaffected, N devices** |
| **Advertising — being discoverable on Radar** | **ONE device only.** §9.3 |

Enabling multi-device *broadcast* requires a change to the derivation itself
(§9.5), which ADR-008 did not price and which is a protocol version change.
**This is the single most likely place ADR-008 bites, and it should go back to
the founder as a scoping fact, not as a defect.**

### 9.5 If multi-device broadcast is wanted: a device discriminator, and its cost

There is no way to have two devices broadcast distinct, unlinkable identities
from a shared root without putting something device-specific into the derivation.
Stated plainly, as required: **multi-device broadcast requires a device
discriminator in the derivation.** The construction:

```
device_key(s)      = HKDF-SHA256(IKM = account_key, salt, info = "device-key" || uint8(s),  L = 32)
daily_key(s, d)    = HKDF-SHA256(IKM = device_key(s), salt, info = "daily-key" || uint32be(d), L = 32)
ephemeral_id(s,d,e)  unchanged, derived from daily_key(s, d)
```

`s` is a small slot index assigned by the server at device enrolment. **It is
never transmitted, never inferable from the air, and never a stable on-air
value** — it is an HKDF input, and the output still rotates every epoch.

**The `info` prefix `"device-key"` is RESERVED by this document as of v0.1 and
MUST NOT be used for any other purpose**, so that adopting this later cannot
collide with something added in between. Reserving it costs nothing.

What it costs, in the order the costs will actually hurt:

1. **It is a protocol version change, and therefore a flag day.** Every derived
   value changes, the salt becomes `radius/ble/v1`, **every crypto vector
   regenerates**, and v0 and v1 devices cannot resolve one another without a
   dual-derivation transition period. **Cheapest by an order of magnitude before
   launch.** This is the reason to decide now rather than when the first user
   asks why their tablet is invisible.
2. **The resolver must derive a fixed number of slots per candidate**, not the
   real number — otherwise the table size publishes "this account has 3 devices",
   which is a linkable per-account attribute and a metadata leak we currently do
   not have. With a fixed cardinality `D = 4`, 500 candidates and a ±1 window,
   that is `500 × 4 × 3 = 6000` HKDF operations per 15 minutes against §6.1's
   1500. Still negligible. **`D` must be a global constant and must never vary
   per account.**
3. **`D` becomes a hard cap on devices per account.** Exceeding it is not a
   graceful degradation; it is another version change.
4. **The operator learns which device, not merely which account.** This is a real
   increment, on an axis ADR-008 already conceded — the operator can already
   derive everything — but it should be written down rather than discovered.
5. **Slot assignment must be server-side and online.** A device cannot self-assign
   without collision risk. Issuance is already online-only, so this adds no new
   class of dependency.
6. **A third-party observer learns nothing new. Nothing.** Invariants 4 and 5 are
   untouched: the frame is unchanged, the on-air value is still a uniform 16
   bytes rotating every epoch, and `s` never appears. **That is the whole
   argument for the discriminator: it pays the operator slightly more so that
   third parties pay nothing — which is exactly the direction ADR-008 already
   chose to trade in.** Compared with a shared eid, which pays *third parties*
   everything in §9.2, it is not a close call.
7. Gain, not cost: revocation granularity improves. A single device can be
   revoked by dropping its slot, without rotating the account root.

**Recommendation:** if multi-device broadcast is wanted at all, adopt the
discriminator **before launch**, as `v1` of the salt, in one change with one
vector regeneration. Do not ship v0 broadcast-from-two-devices under any
circumstances, and do not plan to "add it later" without pricing the flag day.

### 9.6 Self and twin frame rejection — normative

> **A receiver MUST discard, before resolution, any frame whose `ephemeral_id`
> equals any of its own eids within its own accepted epoch window (§6.2).**

Drop code `E_SELF_EID`. The frame MUST NOT create a peer instance, MUST NOT be
counted in any user-visible figure, and MUST NOT be surfaced.

Two reasons. First, without it a device can discover *itself* — via reflection,
a relay, or its own account's second device — and present it to the user as a
stranger standing next to them. Second, it is the cheapest local detector we have
for both duplicate broadcast and replay of our own eid. Implementations SHOULD
keep a per-epoch counter of `E_SELF_EID` drops (counter only, no payload, per
`SPEC.md` §3.6). **A non-zero count means either a duplicate-broadcast bug or
somebody is replaying you, and both are worth knowing about.**

Note that the window is evaluated per epoch under the ring (§8.4), so a device
correctly rejects its own pre-seam eid as well as its post-seam one.
`vectors/key_rotation.json` covers this case.

## 10. Threat model — the operator is now inside it

Supersedes nothing in `SPEC.md` §9; extends it. ADR-008 moved exactly one
adversary across the line, and this section states which one, what it can now do,
and what it still cannot.

### 10.1 Third-party air observer — UNCHANGED, re-verified field by field

The claim ADR-008 makes is that "a passive BLE eavesdropper still learns
nothing". That is a claim this document owns, so it is re-checked rather than
repeated:

| On air | Before ADR-008 | After ADR-008 |
|---|---|---|
| `version` (1 B) | constant `0x01` | constant `0x01` |
| `ephemeral_id` (16 B) | uniform, rotates 15 min | **identical function, identical output** |
| `tx_power_cal` (1 B) | 7-value class, ~2.8 bits of model class | unchanged |
| `flags` (1 B) | 1 defined bit, ~1 bit of platform tell | unchanged |
| advertiser address | RPA, must co-rotate (invariant 5) | unchanged |
| rotation timing | global UTC boundary, no jitter | unchanged |
| total distinguishing budget | ~3.8 bits + signal continuity | **~3.8 bits + signal continuity** |

**Not one byte, bit, or timing parameter on the air changed.** Invariants 4 and 5
hold exactly as written. If a future issuance requirement ever needs something on
the air — a key id, a device slot, an issuance nonce, a version negotiation, a
"which key are you using" hint — **that is a far larger decision than ADR-008
authorised, and it stops at this document and goes back to the orchestrator with
an ADR.** ADR-008 explicitly leaves both invariants intact; anything that touches
the frame is out of its scope, not covered by it.

### 10.2 The operator — NEW, and the reason this section exists

The server generates and retains `account_key` (§2). It can therefore derive
every `daily_key` and every `ephemeral_id` for every account, **past, present and
future**, at negligible cost. Given a BLE capture from any time and place, the
operator can attribute it to an account.

Consequences, from ADR-008 and restated here because implementers need them in
the document they actually read:

- Retroactive deanonymisation is possible. Rotation does not undo it (§8.1).
- We cannot truthfully say "we are unable to identify who was broadcasting."
  Product and marketing copy is constrained by this (ADR-008 M6). Any privacy
  claim implying operator blindness must not ship.
- A key-table breach is a **retroactive location-history** breach, not a
  point-in-time credential breach.
- The conditions under which this is acceptable are M1-M7, in full, as
  requirements rather than hardening. They are release gates.

### 10.3 The bound that actually holds — capability × captures

The operator's derivation capability produces **location data only when combined
with BLE captures.** We hold none, and holding none is the single most effective
control available on this axis. Therefore, at the same status as `SPEC.md` §5.3
F7 — pre-rejected in writing so the argument is short later:

> **P1. Radius MUST NOT operate, fund, contract with, or ingest data from any
> BLE scanning or beacon network, and MUST NOT accept raw, filtered, hashed, or
> truncated `ephemeral_id` observations from clients on ANY endpoint — including
> diagnostics, crash reports, analytics, support tooling, and debug builds.**

This is the exact analogue of decision 28 (RSSI must not cross the shared-module
boundary or reach the server) applied to the identifier rather than the signal,
and it rests on the same reasoning: the value is location data in disguise.

The way it would actually happen is benign and specific: *"discovery is flaky in
the field — let clients upload the eids they saw so we can debug it."* That one
endpoint converts ADR-008's conceded, bounded, capability-only cost into an
operational mass-location system, because we would then hold both halves. It is
pre-rejected. Diagnose discovery with per-epoch **counters** (`SPEC.md` §3.6),
never with observations.

Encounter upload is unaffected and remains `(account, band, epoch)`: the peer is
resolved to an account **on the device, before upload**, so no `ephemeral_id`
ever crosses the network in either direction.

### 10.4 Compulsion and breach

- **Compelled disclosure.** We hold the capability, so the honest answer to a
  warrant is that we can comply. M6 requires a published policy and a
  law-enforcement response process that exists **before** launch, not after the
  first request. This document's contribution is P1: the narrower the data we
  hold alongside the capability, the less a compelled disclosure yields.
- **Breach of the key table.** Retroactive and permanent for captures that
  already exist. Rotation helps only against snapshot exfiltration, and only
  going forward (§8.7). M1/M2/M3/M5 are the controls.
- **The only designs that would have prevented this class** are device-generated
  keys and split derivation (`account_key = HKDF(server_seed, device_secret)`).
  ADR-008 records split derivation as "the most likely revisit". If it is ever
  revisited, note that it composes cleanly with §9.5's device discriminator —
  `device_secret` *is* a device discriminator — and the two changes should be
  taken together as one version bump rather than two.

### 10.5 New abuse-model rows introduced by v0.1

| Attack | Position |
|---|---|
| **Multi-device eid collision** | §9. Blocked in v0 by one-advertiser-per-account (§9.3). Requires a derivation change to unblock (§9.5). The most serious new item. |
| **Rotation-seam observability** | §8.8. None to a third party — rotation lands on the population-wide boundary and nothing about it is on air. |
| **Issuance-channel interception** | M7: single delivery, certificate pinning, **fail closed** if pinning is unavailable (§2.2). |
| **Re-issuance as denial-of-discovery** | §2.4: an attacker with a session can force re-issuance and silently make the victim's real device undiscoverable. Mitigated by rate limiting, audit, and owner notification — not by cryptography. |
| **Stale-ring device** | §8.6: fails to *undiscoverable*, never to *insecure*. Privacy never depends on server reachability. |
| **Operator-plus-capture** | §10.3, P1. The capability is bounded by our not holding captures, and that must be enforced as a rule, not left to inclination. |

### 10.6 What did not change

Tracking over time, multi-receiver triangulation, spoofed presence, sybil,
targeted stalking by third parties, home/work inference, replay, covert channels
in the frame, and permanent linkability via bonding — all exactly as `SPEC.md`
§9. ADR-008 moved one adversary and no invariant.

**Nothing in this section has been validated on hardware, because none of it can
be. It is a design argument, and §5 remains the only part of this document that
a measurement can settle.**
